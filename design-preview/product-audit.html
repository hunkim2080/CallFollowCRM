1. 고객 여정 명세서 (앱의 뼈대)

신규 고객 전화 → … → 잔금까지. 각 단계의 누락·중복·자동화위험·이탈을 본다.

#단계고객/사장 행동앱 동작흐름 누락 위험중복자동화 위험이탈/전환 핵심
1전화 문의고객 전화통화기록 생성권한 없으면 미인식——인식 자체가 시작점
2통화 정리통화 종료통화 후 카드(요약+초안)에이닷 미연결 시 요약 X카드+캐치 동시 가능—요약이 후속의 동력
3문자 발송초안 확인 후 보냄발송+이력발신권한 없으면 실패——응대 속도 = 전환
4접수서 발송견적·계약금 입력→링크링크 prefill(자동발송X)입력 많으면 이탈견적 정보 재입력 가능—여기 이탈 잦음(입력 부담)
5접수서 제출고객 작성폴링 감지→고객 반영고객이 링크 안 엶token 1회(방지됨)주소/금액 자동 덮어씀 ⚠️고객측 이탈 최대 지점
6일정 확정예약일 확인scheduledWorkDate+자동분류제출됐는데 확정 안 함수동 일정 vs 접수 일정 충돌—확정=수익 확보
7계약금받음 표시금액 반영(받음=수동)금액만 있고 받음 표시 누락—받음 자동처리 위험—
8D-1 안내안내 보내기전날 저녁 알림(토글)토글 OFF면 안 감여러 건 개별 알림—신뢰/노쇼 방지
9현장 도착도착5km 자동/수동 버튼위치 OFF면 수동GPS+버튼 중복 가능위치 오탐 도착처리—
10작업 완료완료 누름완료 처리+잔금 확인—협업완료 vs 시공완료 구분—완료=잔금 트리거
11잔금 요청요청/받음완료 3일+ 미수 알림취소 고객에도 갈 수 있음여러 건 개별독촉 오발송회수율 직결
12후기/재문의후기 요청완료 후 카드 옵션재문의 추적 약함——재구매/소개
여정 결론: 흐름은 1~12 연결됨. 가장 큰 이탈 지점 = 4·5(접수서 입력 부담 + 고객 링크 미열람). 가장 큰 로직 구멍 = 11(취소/보류 상태가 없어 잘못된 잔금 독촉 가능 — §7 참고). 자동화 위험 = 5(주소 덮어쓰기)·9(위치 오탐)·11(독촉).

3. 데이터 흐름 + 충돌 우선순위

전체 데이터 표는 앱 로직 진단 §3 참고. 여기선 충돌 정책만 집중.

데이터접수서(고객) vs 수동(사장) 충돌 시 현재 동작이력문제제안
주소접수서가 무조건 덮어씀(updateAddress)없음사장이 적은 주소가 사라질 수 있음다르면 “고객이 새 주소 제출 — 바꿀까요?” 확인
시공일접수서가 덮어씀없음수동 확정일이 덮일 수 있음다르면 확인 후 반영
메모기존 비었을 때만 추가(보존)append—유지
총금액(견적)수동 우선(비었을 때만)없음—(안전)유지
계약금수동 우선(비었을 때만)없음—(안전)유지
핵심 발견: 충돌 정책이 불일치 — 주소·시공일은 덮어쓰고, 돈은 수동 보존. 변경 이력이 전혀 없음. 한 토큰당 1회라 사고 빈도는 낮지만, 주소·시공일 덮어쓰기는 분쟁 소지. → 권장: “고객이 제출한 값이 기존과 다르면 자동 반영하지 말고 확인 후 반영 + 간단 이력”. (오픈 전 검토)

7. 상태값 설계 ⚠️ (중요 발견)

현재: 고객 “상태” enum 은 2026-05-25 폐기(CustomerStatus enum 폐기, Statuses.kt). 지금 상태는 여러 필드에서 파생됨: categoryId(자동: 시공대기🔨/시공완료✅, 또는 수동) + leadHeat(COLD/WARM) + scheduledWorkDate + deposit/balance(+paidAt) + workCompletedAt.

문제 1 — 취소/보류 상태가 없음: 고객이 취소돼도 필드(일정·금액)가 남아 있으면 잘못된 잔금/D-1 알림이 갈 수 있음.
문제 2 — “완료=시공완료”인지 “완료=잔금까지”인지 모호: category ‘시공완료’는 잔금 입금 시 붙는데, workCompletedAt(작업완료)과 별개라 두 “완료” 개념이 공존.
문제 3 — leadHeat(온도): “온도 편집 제거” 결정이 있었으나 코드엔 여전히 사용 중(고객상세·통화후카드·AI컨텍스트). 정리 필요.
제안: 파생 방식은 유지하되, “보류/취소” 명시 플래그 1개를 추가해서 — 취소/보류면 모든 자동 알림(잔금·D-1) 제외. 그리고 “작업완료”와 “정산완료(잔금)”를 화면·알림에서 분명히 구분. leadHeat 는 쓸지/뺄지 확정.

14. 실제 현장 시나리오 테스트

테스트 1 — 부재중→자동문자→재통화→접수서→일정
확인: ① 알림 몇 개 뜨나(부재중자동 + 통화후카드 + 새문자 → 겹침 점검) ② 자동문자가 고객 맞는 번호로만 나가나 ③ 다음 행동이 보이나 ④ 고객 카드가 정확히 갱신되나.
예상 리스크: 비고객일 때 자동문자 오발송 / 발신통화에 카드 중복.
테스트 2 — 고객이 “다음 주 화요일 가능?” 문자
확인: ① AI가 날짜를 멋대로 확정 안 하나(추천은 초안만) ② 사장 확인 후 답장하나.
예상: 일정 확정은 사장 수동이라 안전. 추천 문구만 제공.
테스트 3 — 팀원 현장 출발/도착/완료
확인: ① 사장 알림이 과하지 않나(3명×3=9건?) ② 팀원이 고객 연락처를 못 보나.
예상 리스크: 알림 폭주(출발 알림 선택화 필요).
