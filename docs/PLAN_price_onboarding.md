핵심 사실이 모두 검증됐습니다. 특히 결정적인 것:

- BornStep(온보딩 Step 3) 카피가 이미 **"가격표·답변 템플릿이 자동으로 만들어졌어요"** 라고 쓰여 있음 → 지금은 빈말(가격표 시드 꺼짐). 접근 D가 이 카피를 진짜로 만드는 전제.
- `priceListText()`가 활성 항목을 자동으로 서버 프롬프트 텍스트로 변환 → 가격표만 채우면 AI 품질이 즉시 오름 (별도 배선 불필요).
- 저장 계약: `insert(price=원 단위 Long)`. 서버가 원 단위로 주면 앱은 ×10000 절대 금지. double-multiply가 최대 버그 위험.

이제 최종 기획서를 작성합니다.

# 가격 온보딩 최종 기획서 — "빈 표가 아니라, 이미 채워진 표에서 시작한다"

작성자: 안드로이드 Claude · 근거: 코드베이스 실측(PricingItemEntity / PricingItemRepository / DefaultPricingItems / OnboardingScreen BornStep) + 4개 접근 설계 종합

---

## 0. 한 줄 결론 (사장님이 먼저 읽을 것)

**새 사용자가 온보딩에서 "가격표를 만드는" 일은 없애 버립니다.** 업종만 고르면 막내가 그 업종 가격표를 **미리 채워두고**, 사장님은 나중에 시간 날 때 숫자만 슥슥 고칩니다. 그리고 앱을 쓰다 보면 폰에 있던 옛날 견적 문자에서 막내가 **진짜 사장님 가격**을 몰래 찾아내 "이거 맞아요?" 하고 한 번만 물어봅니다.

즉 **"입력 0으로 시작 → 쓰면서 저절로 정확해짐."** 온보딩에서 가격 때문에 나가는 사람을 0에 가깝게 만드는 게 목표입니다.

## 1. 왜 이렇게 가는가 (설계 판단 근거)

4개 접근을 하나로 안 묶고 **역할을 나눴습니다.** 각각 "언제 마찰이 0인지"가 다르기 때문입니다.

| 접근 | 마찰 0이 되는 조건 | 신규 창업자에게 | 결론 |
|---|---|---|---|
| D 업종 스타터 템플릿 | **항상** (업종만 고르면 됨) | ✅ 완벽 | **출발점(주력)** |
| A 대화형 AI | 타이핑 3~5번 | △ 약간 부담 | 보조(폴백·보강) |
| B 문자 자동추론 | READ_SMS 켜짐 + 과거 견적 있음 | ❌ 둘 다 없음 | **부스터(나중에)** |
| C 사진/붙여넣기 | 단가표를 파일로 갖고 있음 | ❌ 대개 없음 | 보조(선택지) |

→ **온보딩 순간(신규 설치·신규 창업자)에 조건 없이 마찰 0인 건 D뿐.** 그래서 D를 첫 화면 뼈대로 쓰고, A/B/C는 "나중에 정확도를 올리는 층"으로 배치합니다.

핵심 이득 (코드로 검증됨): 가격표를 어떤 방식으로든 채우기만 하면, `priceListText()`가 자동으로 그 항목을 서버 AI 답변추천 프롬프트에 넣습니다. **가격표 채움 = 킬러기능(AI 답변) 품질↑가 즉시 체감됩니다.** 별도 연결 작업이 필요 없습니다.

## 2. 3단계 로드맵 (Phased) — 시간축으로 본 전체 그림

```
[온보딩 30초]          [앱 쓰는 며칠~몇 주]         [필요할 때]
   접근 D                   접근 B                    접근 A / C
업종만 골라도            문자에서 진짜               직접 고치기 /
표가 채워짐      →      가격 몰래 찾아         →     사진·붙여넣기
(대략값, 배지)          "이거 맞아요?" 1회         (가격표 관리 화면)
   ↓                        ↓                          ↓
cold-start 해결        시간 지날수록 정밀화       사장님이 최종 주도
```

- **1단계 (온보딩) = 접근 D:** 빈 표를 없앤다. "대략값"이라도 AI가 답할 수 있게.
- **2단계 (사용 중) = 접근 B:** SMS 권한이 자연스레 켜진 뒤, 백그라운드로 옛 견적 문자를 읽어 초안 개선. 조용한 배너로 확인만.
- **3단계 (상시) = 접근 A/C:** 가격표 관리 화면에서 손으로 고치거나, 사진/붙여넣기로 통째로 넣기.

**MVP는 1단계(D)만.** 이것만으로도 온보딩 이탈 방지 목표의 대부분을 달성합니다.

## 4. AI 역할 · 실제 프롬프트 · 데이터 매핑

### 4-1. 1단계 (D) — 업종 스타터 생성

**서버 엔드포인트 2개** (맥미니 cowork):
- `POST /pricing/starter` — 앱이 `{ownerTrade, ownerRegions, deviceId}` 보내고 즉시 200 (기존 prepare-reply와 같은 fire-and-forget 패턴)
- `GET /pricing/starter/{deviceId}` — 캐시 조회 (suggestions_cache 방식 재사용)

**줄눈은 LLM 안 부름.** 서버가 앱의 DefaultPricingItems와 동일한 18항목을 하드코딩 반환(정확도 검증됨, 비용 0). 타 업종만 LLM.

프롬프트 (system):
```
너는 한국 인테리어/시공 견적 데이터 생성기다.
항목명은 초보 사장님이 고객에게 그대로 읽어줄 수 있는 자연어여야 하고,
가격은 2025~2026 한국(서울/수도권 기준) 시세의 "보수적 중앙값"을 만원 단위로.
확신 없으면 항목을 만들지 마라. 없는 항목/가격을 지어내지 마라.
```
프롬프트 (user):
```
업종: {ownerTrade}, 지역: {regions}.
이 업종에서 가장 흔한 견적 항목 6~12개를 JSON으로.
```

**입력/출력 JSON 스키마:**
```json
// 입력
{ "ownerTrade": "에어컨", "ownerRegions": ["서울"], "deviceId": "..." }

// 출력
{ "items": [
    { "title": "벽걸이 에어컨 설치",
      "priceWon": 100000,        // 반드시 원 단위, 만원 배수
      "unit": "FLAT",            // FLAT | PYEONG
      "category": "COMMON",      // NEW | OLD | COMMON
      "confidence": 0.7 }        // 0~1
  ],
  "coverage": "high" }
```
서버 후처리: confidence<0.4 버림, 만원 배수 아니면 반올림, unit 모르면 FLAT(보수화).

### 4-2. 2단계 (B) — 옛 견적 문자에서 추출

**엔드포인트:** `POST /extract-pricing`. 앱이 발신 문자를 1차 정규식 필터(`만원|만|원|₩|견적|평|㎡` 포함 + 5~500자)해서 batch 전송.

프롬프트 핵심 규칙:
```
- 사장님이 "보낸" 문자의 제시가만 신뢰.
- 계약금·잔금·입금·총액·고객이 부른 예산은 가격에서 제외.
- 같은 항목 여러 번이면 최근/최빈값. 확신 없으면 넣지 마라.
```
출력에 `confidence` + `evidence`(근거 문자 원문 1줄) 포함 → 확인 화면에서 "왜 이 가격?"으로 보여줌.

### 4-3. 3단계 (C) — 사진/붙여넣기 (Vision)

**엔드포인트:** `POST /api/parse-pricelist`. Sonnet 4.6 Vision. 이미지 base64 여러 장 + 붙여넣기 텍스트. STT 아님 → 유료 LLM 정책 OK.

### 4-4. 데이터 매핑 (⚠️ 최대 버그 위험 = 이중곱)

**코드 실측으로 확정된 계약:**
- `PricingItemRepository.insert(price=원 단위 Long)` — price를 그대로 저장.
- 입력 UI(PricingItemsScreen)만 만원 → ×10000.
- `priceListText()`는 `price >= 10000 && price % 10000L == 0L`이면 "N만원" 표시.

→ **철칙: 서버는 항상 원 단위(예 250000)로 준다. 앱은 서버값에 ×10000 절대 안 한다.** 확인 화면은 표시할 때만 `/10000`(만원). 이 계약을 서버 핸드오프 문서에 못박습니다.

| 서버 필드 | → | PricingItemEntity | 규칙 |
|---|---|---|---|
| `title` | → | `title` | trim (repo가 처리) |
| `priceWon` (원) | → | `price` (Long) | **×10000 금지** |
| `unit` "FLAT"/"PYEONG" | → | `unit` | UNIT_FLAT/UNIT_PYEONG 상수와 1:1 |
| `category` "NEW"/"OLD"/"COMMON" | → | `category` | PricingCategory.name과 1:1. **UNKNOWN이면 COMMON**으로 저장(견적 신축모드에서 NEW+COMMON 노출되므로 안전) |
| 배열 index | → | `displayOrder` | |

**"추정" 배지용 컬럼 하나 추가 필요:** DB 마이그레이션으로 `isEstimated: Boolean = false`. D로 채운 항목만 true, 사장님이 값 고치면 false로. (대안: createdAt==updatedAt 근사로 처리 가능하나 명시 컬럼이 깔끔)

### 4-5. 확인/수정 UX 공통 원칙
- **절대 자동 확정 저장 금지.** B/C는 반드시 "이거 맞아요?" 인간 확인 1스텝 후 저장.
- D는 예외적으로 자동 채움 허용(대신 "추정" 배지 + "대략값" 카피로 솔직하게, 절대 "완성" 단정 안 함).
- 확인 카드에서 [맞아요]/[고칠래요]. 고치면 만원칸 인라인 숫자패드 수정.

## 5. 정확도 · 개인정보 안전장치 · 실패 폴백

### 5-1. 정확도 (돈 실수 = 신뢰 붕괴)
- **이중곱(×10000 두 번) 방지:** 서버=원 단위 계약 고정 + 앱 매핑에서 곱 금지 + **단위테스트로 250000 → "25만원" 왕복 검증** (사장님 룰: 순수함수는 단위테스트).
- **금액 sanity 가드(앱단):** priceWon이 1,000원 미만이거나 5,000만원 초과면 경고 아이콘 + "이 금액 맞을까요?" 재확인.
- **단위 오인식(평당↔정액, 10~30배 오차):** 서버가 모르면 FLAT로 보수화. 가격표 화면에서 "평당"/"개당"을 크게 표시해 눈으로 검증.
- **hallucination(안 한 말 창작):** 프롬프트에 "지어내지 마라, 애매하면 빼라" + confidence 필드. confidence 낮으면 회색·미체크.
- **B의 특수 위험(잔금·총액·고객예산을 단가로 오인):** 프롬프트 명시 배제 + few-shot 반례 + evidence 원문 노출.
- **D 추정값 hedge:** 사장님이 안 고친 추정 항목은 AI 답변에서 "대략 ○○선입니다, 정확히는 확인 후" 톤 강제(서버 prepare-reply에 isEstimated 플래그 전달).

### 5-2. 개인정보
- **온보딩에서 READ_SMS 요구 안 함.** B는 권한이 다른 자연스러운 순간(상담함/채팅)에 이미 켜졌을 때만 백그라운드로 동작. "내 문자를 왜 읽어?" 거부감으로 온보딩 이탈 방지.
- 문자 → 서버 전송은 가격 신호 있는 것만 1차 필터 후 batch. 결과는 owner_phone 키로 캐시(재과금 방지).
- LLM API 키는 맥미니 서버에만. STT 안 씀(전부 텍스트/Vision).

### 5-3. 실패 폴백 (막다른 길 없음)
- D 서버 실패/오프라인 → 줄눈은 로컬 시드로 즉시 채움. 타 업종은 빈 표 + "직접 추가" (거짓 배지 안 띄움).
- B 문자 없음/부실(항목<3) → 접근 A(3줄 대화) 또는 빈 표.
- C 못 읽음/빈 결과 → "다시 찍거나 직접 입력할게요", 타임아웃 20초.
- **최종 안전망:** 무엇이 실패해도 가격표 관리 화면에서 손 입력 항상 가능. 앱은 가격표 비어도 정상 작동.

## 7. 비용

- **D:** 사용자당 딱 1회. 줄눈=0원(하드코딩), 타 업종만 1콜(입력 ~300 / 출력 ~600 토큰) ≈ **사용자당 $0.01 미만.**
- **B:** 1회성, 입력 6~10k 토큰 ≈ $0.04/사용자. prompt caching으로 반복 시 더 저렴.
- **C:** 사진 1~3장 ≈ $0.05~0.1/사용자.
- 전부 온보딩/최초 1회성 → 답변추천 대비 총량 무시 가능. STT 0원.

## 8. 언제 무엇이 주력/보조인가 (요약)

- **주력 = D (업종 스타터).** cold-start를 조건 없이 마찰 0으로 해결. 이미 있는 BornStep 카피와 정합. 최저 비용·최저 위험.
- **부스터 = B (문자 추출).** 기존/경력 사장님에게 강력. 단 권한·문자이력 조건부라 온보딩 앞세우지 않고 "쓰다 보면 저절로" 서프라이즈로.
- **보조 = A (대화 3줄) / C (사진·붙여넣기).** D가 못 채운 업종·폴백, 그리고 사장님이 직접 주도하고 싶을 때.

**한 문장:** D로 출발선을 채우고(입력 0), 앱을 쓰는 동안 B가 진짜 가격으로 몰래 교정하며, A/C로 사장님이 마무리한다. "완벽한 가격표"가 아니라 "AI 답변이 쓸만해지는 최소 가격정보"를 온보딩 30초 안에 확보하는 것이 목표다.
