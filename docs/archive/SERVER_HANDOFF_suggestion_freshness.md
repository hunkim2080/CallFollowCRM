# 서버 핸드오프 — 추천 답변 정합성(stale/덮어쓰기) 경량 개선

작성: 2026-06-27 · android(Claude Code) → cowork(맥미니)
관련: 추천 답변이 "옛 맥락"으로 보이는 문제. 2차 의견(대형 시스템용 conversation_version·job 테이블)을
**1인 시공자 규모에 맞게 경량화**한 합의안. 앱 측은 이미 구현(아래 commit).

---

## 배경 / 합의

- 추천은 서버가 **번호별 1벌 캐시**. 앱은 진입 시 그 캐시를 즉시 표시.
- 문제: 캐시가 옛 고객 메시지 기준이어도 최신인 척 보였고, 늦게 끝난 옛 생성이 새 결과를 덮을 수 있음.
- **정책 결정(사장님): (A) 부드럽게** — stale 이면 옛 추천 흐리게 + 자동 새 생성 + 스르륵 교체. 하드 차단 X.
- **경량 원칙**: conversation_version 카운터/대화 엔티티/recommendation_jobs 테이블은 **만들지 않음**.
  앱이 메시지 출처(소스 오브 트루스)이므로, **"기준 고객 메시지 시각(ms)"** 을 버전 표시로 그대로 씀.

---

## 앱 측(완료) — 참고

- 진입/새 문자 시 캐시가 stale(추천 `based_on_received_at_ms` < 현재 최신 고객 메시지 시각)이면 **자동 재생성**(중복 가드 있음).
- stale 동안 옛 칩 흐리게 + "고객 새 문자 N개 안 반영", 생성 실패 시 "다시 시도" 표시.
- prepare 요청에 이미 **`latest_message_received_at_ms`(고객 마지막 메시지 시각)** 를 보냄. (기존 PrepareContext)
- commit: (아래 SYNC 참조)

> 참고: RING-GO 는 **사장님이 마지막으로 말한 대화면 추천을 아예 숨김**. 그래서 "버전"을 고객 메시지 시각만으로
> 잡아도 충분함(사장님 발신까지 버전에 넣는 대형-시스템식 처리 불필요).

## cowork 측 할 일 (서버, 작게)

### 1. 캐시에 "기준 메시지 시각" 저장 + 응답 반환 (이미 거의 됨 — 확인/보강)
- `/api/suggestions/prepare` 가 받은 `latest_message_received_at_ms` 를 그 생성 결과 캐시에 **저장**.
- `/api/suggestions/{digits}` (fetch) 응답에 **`based_on_received_at_ms`** 로 그대로 반환.
  (앱이 이 값으로 stale 판정. 지금도 ReplySuggestions.basedOnReceivedAtMs 로 받고 있으니, 비어있지 않게만 확인.)

### 2. ⭐ 덮어쓰기 가드 (핵심) — 늦게 끝난 옛 생성이 새 추천을 못 덮게
- prepare 가 LLM 생성을 마치고 캐시에 저장할 때:
  ```
  if 새_결과.based_on_received_at_ms < 기존_캐시.based_on_received_at_ms:
      # 늦게 끝난 옛 메시지 기준 결과 → 최신 캐시를 덮지 않음 (폐기 또는 무시)
      return  # active 캐시 갱신 안 함
  else:
      # 같거나 더 최신 기준 → 정상 저장
  ```
- 이유: 앱이 자동 재생성 + 사장님 ↻ 가 거의 동시에 날아가는 경우(레이스), **순서 뒤바뀐 응답이
  최신 추천을 거꾸로 덮는** 사고 방지. (1인 규모라 드물지만 가드는 싸고 안전)

### 3. (선택) 같은 기준 중복 생성 억제 — in-flight 가드
- 같은 `(digits, based_on_received_at_ms)` 로 **생성 중인 작업이 있으면** 새 prepare 를 무시(또는 join).
- 없으면 생략 가능(앱이 이미 중복 호출 가드함). 비용 더 줄이고 싶을 때만.

### 4. (선택) MMS ready — 사진 메시지면 생성 보류
- 마지막 고객 메시지가 사진이고 아직 파싱/저장 전이면 추천 생성 보류 → 반쪽 답 방지.
- 앱은 MMS 다운로드 완료 후에 prepare 를 보내므로(MmsDownloadService), 서버는 받은 시점=ready 로 봐도 무방.
  필요 시에만.

## 일부러 **안 하는** 것 (과설계 방지, 1인 규모)
- ❌ conversation 엔티티 + version 카운터 신설 (앱이 메시지 소스라 불필요)
- ❌ recommendation_jobs 상태 머신 테이블 (동시성 거의 없음 — in-flight 가드면 충분)
- ❌ 추천 이력 여러 벌 보관 (번호당 1벌 + 덮어쓰기 가드)

→ 필요한 정합성(번호표 기준 + 덮어쓰기 방지)은 **2번 가드 하나**로 대부분 달성.

## 우선순위
1. **2번(덮어쓰기 가드)** — 필수. 이거만 해도 "거꾸로 가는" 핵심 사고 막힘.
2. **1번(저장/반환 확인)** — 이미 동작 중이면 OK 확인만.
3. 3·4번 — 비용/품질 더 조이고 싶을 때.
