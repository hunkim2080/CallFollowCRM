# 추가금(Extra Charge) 기능 설계안 — 2026-06-04

> 발단: 사장님 "오늘 추가금 5만원 받았는데 총금액이 바뀐 거잖아. 어떻게 입력해?"
> 즉시 대응(완료, commit 별도): 고객 카드 일정·정산에 **[금액 수정]** 버튼 복구 → 총금액 직접 정정 가능.
> 이 문서 = 그다음 "추가금" 개념을 제대로 설계(사장님 모델 확정 후 구현).

## 문제
시공 중/후에 추가 비용이 자주 생김(추가 시공, 자재 추가, 출장비 등). 지금은:
- 고객의 금액이 `totalAmount` 단일 필드 하나뿐 → 추가금이 생기면 총액만 덮어쓰고 **"무엇이 얼마 늘었는지" 이력이 안 남음**.
- 받은 추가금을 정산/현금흐름에 따로 또 적어야 함(이중 입력).

## 목표
1. 추가금을 항목으로 기록(금액 + 내용메모 + 날짜).
2. 고객 총액 = 기본 견적 + 추가금 합계 (자동).
3. 받은 추가금은 정산 "받은 돈"·현금흐름에 자동 반영(한 번 입력).
4. 고객 카드에서 추가금 내역 한눈에.

## 모델 후보

### ⓐ extra_charges 테이블 (정석 · 권장)
새 Room 엔티티:
```
ExtraChargeEntity(
  id: Long PK,
  customerId: Long,        // FK → customers
  amount: Long,            // 원 단위
  memo: String,            // "현관 추가 시공" 등
  createdAt: Long,
  receivedAt: Long?        // null=아직 안 받음 / 값=받은 시각
)
```
- 고객 effective 총액 = `totalAmount + Σ(extra.amount)`.
- 정산 received = 기존 + Σ(받은 extra). 현금흐름 = 받은 extra 를 그 날짜 income 으로.
- 고객 카드 일정·정산: 기본 견적줄 + 추가금 줄들(메모·금액·받음체크) + [+ 추가금].
- **작업량**: DB 마이그레이션(v↑) + DAO/Repo + UI(추가/목록/받음체크/삭제) + 정산·통계의 총액/받은돈 계산이 effective 총액을 쓰도록 수정(여러 화면).
- 장점: 이력 명확·항목별·견적서에도 반영 가능. 프로토 est-break(견적 내역) 정신과 일치.
- 단점: 가장 큼(여러 화면 정산 계산 손봐야).

### ⓑ 총액 반영 + 현금흐름 기록 (경량 · 마이그레이션 없음)
- "추가금 추가" 액션: 금액+메모+받음여부 입력 → ① `totalAmount` 를 그만큼 증액 ② 받았으면 기존 manualCash income 으로 기록(label="{고객} 추가금: {메모}", 오늘 날짜).
- 이력 = 현금흐름 로그(+총액엔 반영). 별도 테이블·마이그레이션 없음.
- 장점: 빠르고 안전(기존 테이블만). 이중입력 해소.
- 단점: 고객 카드에 "추가금 목록"으로는 안 보임(총액만 커지고, 내역은 현금흐름에). manualCash 가 customerId 링크가 없어 고객별 추출 약함.

### ⓒ 단일 필드 (너무 제한적 — 비권장)
`extraAmount`+`extraMemo` 한 쌍만. 추가금 여러 번이면 부족.

## 추천
- **이력·항목이 중요하면 ⓐ**, **빠르게 실용만이면 ⓑ**.
- 사장님 실제 패턴(추가금이 한 건당 1~2번 정도인지, 견적서에 반영돼야 하는지)에 따라 결정.

## 결정 대기 (사장님)
- 어떤 모델로 갈지(ⓐ/ⓑ).
- 추가금이 견적서(직인 문서)에도 항목으로 들어가야 하는지.
- "안 받은 추가금"도 미수로 관리해야 하는지(ⓐ면 자동 지원).
