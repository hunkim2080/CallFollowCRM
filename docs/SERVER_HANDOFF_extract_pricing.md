---

## 왜 필요한가 (한 줄)
신규 사장님이 가격표를 손으로 안 채워도, **사장님이 예전에 고객에게 보낸 견적 문자**를 AI 가 읽어서
"이 사장님은 이런 항목을 이 가격에, 이런 기준으로 판다" 를 자동으로 뽑아 가격표를 채운다. 사장님은 확인·수정만.

## 엔드포인트
`POST /extract-pricing` — 앱이 후보 문자 배열 전송, 서버가 Claude 1콜로 구조화 항목을 추출해 반환.
- 동기 반환 권장(온보딩 1회성, 사장님이 로딩 스피너 보며 대기해도 OK). 오래 걸리면 스타터 패턴(POST→GET 폴링)으로 해도 무방.
- 캐시 키 = deviceId (재과금 방지). 같은 deviceId 재요청은 캐시 반환.

## 입력 JSON
```json
{
  "deviceId": "…",
  "ownerTrade": "줄눈",                 // 온보딩에서 고른 업종. 힌트로만 사용(문자가 우선).
  "candidates": [
    { "body": "샤워부스 벽 3면은 35만원, 화장실 전체벽은 70만원...", "dateMs": 1782694852000 },
    { "body": "6월 25일 일정확정 위해 예약금 100,000원...", "dateMs": 1782455952000 }
  ]
}
```
- `candidates` 는 앱이 이미 1차 필터(가격신호 있는 보낸문자)+중복제거 한 것. 그래도 **예약금 안내·입금확인·잔금 통보 같은 '견적 아님'이 섞여 있다** → 서버가 걸러야 함(아래 프롬프트).
- 최신순 정렬돼서 옴. 개수는 보통 수십~150개.

## 출력 JSON (엄격 — 스타터와 동일 계약 + basisText)
```json
{
  "status": "ready",
  "items": [
    {
      "title": "샤워부스 벽 3면",          // 사장님이 고객에게 읽어줄 자연어 항목명
      "priceWon": 350000,                 // ⚠️ 반드시 '원 단위' 정수(만원 배수 권장). 35만원 → 350000
      "unit": "FLAT",                     // "FLAT"(정액/개당) | "PYEONG"(평당)
      "category": "COMMON",               // "NEW"(신축) | "OLD"(구축) | "COMMON"(공통)
      "basisText": null,                  // 가격 '기준' 한 줄. 조건부일 때만. 예: "구축은 현장서 0~10만원 조정", "오염도에 따라 다름", "평수에 따라 다름". 없으면 null
      "confidence": 0.9                   // 0~1
    }
  ]
}
```

### ⚠️ 최우선 계약 — priceWon 은 '원 단위' (스타터와 동일, 어기면 견적 10000배 틀어짐)
- 앱 `PricingItemRepository.insert(price=priceWon)` 로 **그대로** 저장. 앱은 ×10000 안 함.
- 35만원 → `350000`. `35` 나 `35만` 금지. 앱에 단위테스트(PricingItemFormatTest)로 못박음.
- `unit`/`category` 대문자 그대로. 모르면 unit=FLAT, category=COMMON.

### basisText (이 엔드포인트의 핵심 차별점)
- 문자에 "구축은 조정", "오염도 심하면 추가", "평수마다 다름" 같은 **가격 판정 기준**이 있으면 한 줄로 뽑아 담는다.
- 무조건 채우지 말 것 — 문자에 조건 언급이 **명시적으로 있을 때만**. 없으면 `null`.
- 이게 AI 답변 품질의 핵심: "왜 그 가격인지"까지 알아야 상담 답변이 사장님처럼 나온다.

## 시스템 프롬프트 골자 (Claude Sonnet 4.6)
```
너는 한국 인테리어/시공 사장님의 '보낸 문자'들을 읽고, 그 사장님의 가격표를 복원하는 추출기다.
입력은 사장님이 고객에게 보낸 문자 여러 개다. 다음을 지켜라:

1. 견적/단가 문자에서만 항목을 뽑아라. 아래는 '견적 아님' → 무시하라:
   - 예약금/계약금 안내(예: "예약금 100,000원"), 잔금 통보(예: "잔금 125만원입니다"), 입금확인,
     계좌 안내, 접수서 링크, 시공 완료 인사, 앱/서비스 홍보 문자.
   - 즉 '특정 시공 항목의 단가'가 아니면 버려라. 총액·예약금·잔금은 항목이 아니다.
2. 같은 항목이 여러 문자에 다른 가격으로 나오면: 가장 최근(dateMs 큰) 값을 우선. 신축/구축이 다르면 category 로 분리.
3. 가격 '기준'(조건부 가격)이 문자에 명시되면 basisText 한 줄로. 없으면 null. 지어내지 마라.
4. 확신 없으면 항목을 만들지 마라(confidence<0.5 는 버려라). 없는 항목/가격을 상상하지 마라.
5. 항목명은 초보 사장님이 고객에게 그대로 읽어줄 자연어. 6~15개 정도로 정리(중복 병합).
6. priceWon 은 원 단위 정수(만원 배수 권장).
출력은 위 JSON 스키마만. 설명 문장 붙이지 마라.
```
user: 후보 문자들을 `[dateMs] 본문` 형태로 이어붙여 전달. `ownerTrade` 는 참고 힌트로 명시.

## 서버 후처리 (권장)
- confidence<0.5 버림. priceWon 만원 배수로 반올림(선택). unit/category 이상값 → FLAT/COMMON 보정.
- basisText 길이 제한(예: 40자) — 너무 길면 잘라 저장. 개행 제거.
- 항목 상한(예: 20개)로 컷.

## 프라이버시 / Play 정책
- candidates = 사장님 '본인이 보낸' 문자. 고객 수신정보(번호·이름)는 앱이 안 보냄(본문만).
- 업로드는 앱에서 **동의 게이트**(toneUploadConsented 재사용) 통과 후에만 호출된다 — 서버는 동의 여부를 신뢰.
- 서버는 본문을 **처리 후 로그에 남기지 말 것**(추출 결과 items 만 캐시). 원문 장기보관 금지.

## 기술 메모
- Python 3.9 → `Optional[...]` 사용(PEP604 `X | None` 금지, get_type_hints 502).
- 비용: 사용자당 1회, 입력 ~15~25k / 출력 ~1k 토큰 ≈ $0.05~0.08. 온보딩 1회성이라 무시 가능. prompt caching 은 매 사용자 본문이 달라 효과 적음.
- 실측(사장님 폰): 보낸 MMS 최근1년 1,323 → 가격신호+dedup 후 앱이 보내는 후보 ~수십~150개.
